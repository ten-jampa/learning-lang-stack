Lesson 0003 — Boundaries: read-only vs write tools

One thing: prove that an agent's powers equal its tool list — by building two agents that differ in exactly one tool and watching one succeed where the other refuses. ~20 min. Needs .env key. Assumes lessons 1–2.

1. Three new words, then code

1. Read tool vs write tool — a read tool only looks (get_order returns a record, world unchanged). A write tool changes something outside the conversation (issue_refund appends to a ledger, sends an email, deletes a row). The code difference is nothing special — any function with side effects is a write tool. The spec difference is everything: write tools are the ones that need approvals, limits, and audits.
2. Routing — with two tools, the model picks which to call from their docstrings, each turn. You don't write if/else logic; the docstrings are the dispatch table. That's why lesson 2 insisted the docstring is the manual — now two manuals compete.
3. Boundary by absence — the agent from section 2 has no refund tool at all. When asked to refund, it has no tool call to make, so it answers in words (refusal + alternative). Nothing was "blocked" — the power was never granted. Enforcement by construction, not by instruction.

One practical note before the code: a message's content is usually a plain string, but some models (including Haiku) sometimes return a list of blocks (thinking + text). The 4-line text_of helper below reads either form — defensive reading you'll reuse in every lesson from here on.

2. Build it, line by line

Step 1. Terminal, repo root. Two real Haiku calls this lesson (still fractions of a cent total), ~30–60 s.
Step 2. Paste this block. Watch for the two contrasting endings: 
.venv/bin/python -c "
from dotenv import load_dotenv
load_dotenv()
from langchain.agents import create_agent
ORDERS = {'42': 'veg momos x2'}
REFUNDS = []
def get_order(order_id: str) -> str:
    '''Look up an order by ID. Read-only.'''
    return ORDERS.get(order_id, 'unknown order')
def issue_refund(order_id: str) -> str:
    '''Issue a refund for an order. WRITES state.'''
    REFUNDS.append(order_id)
    return f'refunded {order_id}'
def text_of(msg):
    c = msg.content
    if isinstance(c, str):
        return c
    return chr(10).join(b.get('text', '') for b in c if isinstance(b, dict) and b.get('type') == 'text')
full = create_agent(model='claude-haiku-5-5', tools=[get_order, issue_refund], system_prompt='You are a support assistant')
readonly = create_agent(model='claude-haiku-5-5', tools=[get_order], system_prompt='You are a support assistant')
r1 = full.invoke({'messages': [{'role': 'user', 'content': 'refund order 42'}]})
print('FULL:', text_of(r1['messages'][-1])[:100])
print('REFUNDS:', REFUNDS)
r2 = readonly.invoke({'messages': [{'role': 'user', 'content': 'refund order 42'}]})
print('READONLY:', text_of(r2['messages'][-1])[:200])
"
# expect: FULL refunds + REFUNDS ['42']; READONLY refuses, REFUNDS untouched by it
Step 3. Errors? Same triage as lesson 2 (AuthenticationError → .env; ModuleNotFoundError → folder/venv). New possible surprise: the readonly agent looks up order 42 before refusing — that's routing working as designed (it used the one tool it has, then answered the rest in words).

What just happened, mapped to the three words:

  • REFUNDS list = the "outside world". issue_refund mutates it → write tool. get_order only reads → read tool.
  • The full agent routed: refund request → issue_refund docstring matched → tool call → REFUNDS == ['42']. Proof in data, not vibes.
  • The readonly agent shows boundary by absence: no refund tool exists in its world, so no tool call was possible. Same prompt, same model, different list, different powers.
Tangible win: you can now scope "different specs and boundaries" for real: read-only support agent vs empowered one, differing by exactly one list entry. This is the mission's core skill in miniature.
